## Спецификация структуры базы данных символов (RON DSL), редакция 2

База данных представляет собой набор файлов конфигурации в формате RON. Корневым элементом файла является анонимная структура, содержащая обязательный блок метаданных и независимый плоский список деклараций (entries).

### Принципы

- **Data-driven.** Всё расширяемое лежит во внешних файлах и читается в runtime.
- **ICU как источник Unicode-фактов.** Официальные имена, категории, скрипты, версию появления и прочие свойства Unicode база не дублирует: GUI и поиск обращаются к ICU напрямую. База хранит только то, чего в ICU нет: рецепты, привязки, группировку, вариации, представления (HTML/LaTeX), поисковые токены.
- **Значение символа абстрагировано от представления.** Запись не обязана быть одним `char` (см. раздел 3).
- **Запись = Источник + Свойства.** Источник определяет, *какие значения* порождает запись (один символ, список, матрица…). Свойства одинаковы для всех типов и могут переопределяться локально (см. разделы 4 и 6).
- **Повторы убираются шаблонами.** Общие части значений выносятся на уровень записи: `{имя}` подставляет переменную участника или ячейки, `value_sequence` задаёт последовательные code points, `${id}` ссылается на другую запись (см. «Сокращённая запись списков members»).
- **Ядро не зависит от GUI.** Блоки `ui` необязательны для работы ядра.

## 1. Метаданные файла (Корневой контейнер)

Каждый файл начинается с заголовка, который определяет контекст, пространство имён, описание и приоритеты набора записей.

```ron
(
    metadata: (
        id: "diacritic",                        // Уникальный строковый ID файла
        namespace: "diacritic",                 // Пространство имён записей файла (необязательно, см. раздел 2)
        name: "Diacritic Marks",                // Имя категории для отображения
        order: 1,                               // Порядок сортировки в интерфейсе
        description: "Diacritic marks and related characters",
        // Предложено, ранее не обсуждалось:
        schema_version: 2,                      // Версия формата файла
        requires: ["latin"],                    // Файлы, которые должны быть загружены раньше
    ),
    entries: [
        // Список записей Entry разных типов
    ],
)
```

## 2. Идентификаторы и пространства имён

Полный идентификатор записи в пространстве имён имеет вид `namespace:local_id`, например `diacritic:acute`, `latin:upper_letter_a`. Запись, не входящая ни в одно пространство имён, имеет id без префикса (`ice_cube`).

**Примечание об устаревшем префиксе `lat_`.** В старой программе принадлежность записи к латинице кодировалась префиксом в id (`lat_c_let_a`). Теперь её задаёт пространство имён, и в реальной базе локальные id латиницы выглядят как `upper_letter_a`, а полные как `latin:upper_letter_a`. В примерах этой спецификации `lat_*` в локальных id (`id_template: "lat_{case}_letter_{letter}"`) оставлен лишь как подсказка «это запись латиницы», чтобы не повторять метаданные с пространством имён в каждом примере. Там, где пространство имён указано явно (`latin:...`), префикс `lat_` опущен. Новым записям этот префикс давать не нужно.

- Внутри файла записи объявляются с **локальным** id (`id: "acute"`), а полный id собирается из `metadata.namespace`. Запись может явно указать другое пространство через `namespace: "..."`. Если у файла нет `namespace`, его записи не входят ни в одно пространство, и их id совпадает с локальным.
- **Ссылки.** На запись в пространстве имён снаружи этого пространства ссылаются только полным id (`diacritic:acute`). Внутри пространства имён (в любом файле с тем же `namespace`) пространство можно опустить: `acute`. Короткая ссылка разрешается сначала среди записей пространства файла, затем среди записей без пространства имён. Если запись без пространства совпадает по id с записью внутри пространства, приоритет у записи из пространства (таких случаев не ожидается). Из файла без пространства имён короткая ссылка ищет только записи без пространства.
- Пространство имён является **выборкой**: паттерн `diacritic:{accent}` перебирает все записи пространства `diacritic`, а `{accent}` получает локальный id. Именно это используется в типе 6 для автоматической сборки акцентированных символов (см. тип 6).
- **В разрешённой записи id и пространство имён не хранятся полями.** После развёртывания полный id (`namespace:local_id`) становится ключом хранилища «полный id → Symbol». Поиск по полному id это обращение к хэш-таблице без обхода записей. Пространство имён входит в id и при необходимости выделяется разбором строки до первого `:`; отдельного свойства у записи нет. Слой файла (метаданные и объявления с локальным id) этим не меняется.
- **Зарезервированные символы.** `:` отделяет пространство имён от локального id (по первому `:`). `+` отделяет компоненты состава и встречается в id только у записей, порождённых ссылочной матрицей (тип 6): `latin:upper_letter_a+acute`. В id, написанных вручную (`id` и `id_template` обычных записей), `+` и `:` не допускаются; загрузчик это проверяет. Так вручную написанный id никогда не совпадёт с автоматически сгенерированным составным. Сами id различаются как целые строки: `upper_letter_a` и `upper_letter_a+acute` это два разных ключа хранилища, а `+` в них обычный символ ключа. Если локальные id меток из разных пространств совпадут и id составных записей столкнутся, это поймает валидация дубликатов id.
- Пользовательские файлы и моды работают в собственных пространствах и не конфликтуют с базовыми. Изменение чужой записи делается только явным переопределением (см. раздел 6).

## 3. Значение символа (Value)

Поле `value` задаёт результат записи. Это не `char`, а тип с несколькими представлениями:

| Конструкция    | Что хранит                                   | Назначение                                                                                                                                                                                                                                     |
| ------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Cp(0x0301)`            | Один code point как число                 | Обычный одиночный символ. Число остаётся доступным напрямую.                                                                                                                                         |
| `Chr('Á')`             | Один символ-литерал                  | То же, что `Cp`, но читаемо в данных. Внутри приводится к `Cp`.                                                                                                                                              |
| `Seq([0x042B, 0x0301])` | Последовательность code points      | Символ из нескольких code points: базовый + combining, ZWJ-последовательности, variation selectors, пары Regional Indicators, Unicode Tags и т. п.                                                     |
| `RawTxt("…")`          | Произвольная строка как есть | Всё, что не укладывается в остальные формы: готовый текст, служебные последовательности. Не нормализуется и не валидируется на графемы. |

Сокращение для обратной совместимости: `codepoint: 0x0301` равно `value: Cp(0x0301)`.

### Правила

- **Валидация `Cp`/`Seq`.** При загрузке `u32` проверяется (диапазон до 0x10FFFF, не суррогат) и превращается в `char`. В Rust значение хранится как `char`/`Box<[char]>`; числовой код доступен через `as u32`.
- **Нормализация** задаётся полем `normalization: Preserve | Nfc | Nfd | Auto` (по умолчанию `Preserve`).
  - `Auto` даёт NFC там, где он схлопывает последовательность в один символ, и сохраняет `Seq` там, где предкомпозита нет.
  - Нормализация может менять порядок combining marks (по canonical combining class), поэтому при сравнении и индексации используется нормализованная форма, а исходная запись автора сохраняется.
  - Результат NFC зависит от версии таблиц Unicode, поэтому версия таблиц фиксируется при сборке индекса.
- **Графемы.** `Cp`, `Chr` и `Seq` по умолчанию должны образовывать один grapheme cluster. Исключения помечаются `allow_multi_grapheme: true`. Для `RawTxt` проверка не выполняется.
- **Эквивалентность.** Загрузчик вычисляет канонически эквивалентные формы (`Á` и `A + U+0301`), чтобы поиск и обратный поиск находили оба варианта.
- **Результат композиции** (`Compose`, `Computed`) имеет тип `Precomposed(char) | Sequence(Vec<char>)`, а не просто число.

Набросок типов Rust:

```rust
enum Value {
    Cp(char),
    Seq(Box<[char]>),
    RawTxt(String),
    // Chr(..) при разборе приводится к Cp
}

enum Normalization { Preserve, Nfc, Nfd, Auto }
```

## 4. Структура записи: Источник + Свойства

Каждая запись состоит из **источника** (одно из полей `value`, `members`, `matrix`, `referenced_matrix`, `generator`) и общего набора **свойств**:

| Свойство         | Назначение                                                                                                                                       |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id` / `id_template` | Идентификатор или шаблон идентификаторов                                                                              |
| `normalization`        | Политика нормализации значения                                                                                                 |
| `collections`          | Коллекции, в которые входит запись                                                                                            |
| `variation_of`         | Ссылка на базовую запись (опционально)                                                                                     |
| `hidden`               | Не показывать в основных списках GUI                                                                                           |
| `recipes`              | Рецепты Forge/Compose, приводящие к этому символу                                                                            |
| `value_sequence`       | Последовательные значения участников списка (см. «Сокращённая запись списков members») |
| `ui.display_groups`    | В какие группы и вкладки GUI попадает запись                                                                             |
| `binds`                | Привязки клавиш по режимам (см. раздел 8)                                                                                   |
| `options`              | Прочие опции (`layout_titles` и др.)                                                                                                       |
| `repr`                 | Представления, которых нет в ICU (HTML-сущность, LaTeX)                                                                    |
| `tags`                 | Дополнительные поисковые токены                                                                                               |

Свойства, которые можно получить из ICU (официальное имя, категория, скрипт, версия Unicode, числовые ссылки), в базе **не хранятся**.

### Рецепты и привязки живут внутри записи

Рецепт и привязка к клавише записываются прямо в записи, потому что GUI отображает их в одном порядке с символами. Вкладка «Рецепты» отличается от вкладки «Быстрые клавиши» только тем, что читает свойство `recipes`, а не `binds`.

```ron
recipes: ["A${diacritic:acute}", "A´"],   // Каждый рецепт: строка с возможными ссылками ${...}
binds: [
    Bind(key: Latin("A"),    modifiers: [RightAlt]),   // Привязка по наборам; набор определяет раскладочную семантику
    Bind(key: Cyrillic("Ф"), modifiers: [RightAlt]),
],
```

Бинд одновременно показывается в GUI и регистрируется как реальная комбинация. В старой программе `fast_key` был лишь визуальным представлением. Структура, режимы, клавиши, модификаторы и правила совпадения описаны в разделе 8.

### Рецепты

Рецепт это строка символов, которую пользователь вводит, чтобы получить значение записи. В строке допускаются ссылки на другие записи вида `${id}`: вместо ссылки подставляется `value` указанной записи.

```ron
recipes: ["A${diacritic:acute}"],   // "A" + combining acute; после NFC даёт «Á»
recipes: ["AE", "Ae"],              // У записи может быть несколько рецептов
```

- **Подстановка.** `${...}` заменяется значением записи (для `Seq` целой последовательностью). Подстановка выполняется при развёртывании записей, до нормализации; сопоставление ведётся уже по получившейся строке.
- **Форма ссылки.** Полная форма: `${namespace:id}` (для записи без пространства имён просто `${id}`). Короткая форма (`${acute}`, как в старом DSL-KeyPad) допустима внутри пространства имён и разрешается по правилам раздела 2. Ссылка на запись другого пространства всегда полная.
- **Литерал `$`** записывается как `$$`.
- **Неразрешённая ссылка.** Рецепт пропускается с предупреждением в логе загрузки; запись остаётся.
- **Валидация.** Одинаковые рецепты у разных записей это ошибка. Рецепт, являющийся префиксом другого (`A` и `AE`), допустим: выбор между ними (самое длинное совпадение, ожидание следующего символа) решает механизм ввода, а не база.

### Теги

Теги это обычное поле записи, массив строк, как и рецепты. Они заполняются при инициализации, и на них распространяются те же шаблоны (`{имя}` из переменных участника или ячейки, `${id}`). У большинства символов теги в записи не пишутся (пустой массив): их создают общие правила, объявленные за пределами записей. Сами эти правила и локализация названий не входят в структуру записи и в эту спецификацию.

### Приоритет свойств

Значение свойства берётся в порядке **Member > Entry > значения по умолчанию файла**. Member может переопределить любое свойство локально, не затрагивая остальных участников.

### Сокращённая запись списков members

Для записей с `members` (типы 2 и 3) есть два сокращения, которые убирают повторы.

**1. Последовательные значения (`value_sequence`).** Если code points участников идут подряд, значение задаётся один раз на уровне записи:

```ron
value_sequence: (start: Cp(0x02E5)),              // step: 1 по умолчанию
value_sequence: (start: Cp(0x02E9), step: -1),    // в обратном порядке
value_sequence: (start: Cp(0x0100), step: 2),     // через один (пары Ā ā, Ă ă, …)
```

- Значение участника = `start + индекс × step`, где индекс это позиция участника в списке `members`. Знак `step` задаёт направление, а величина шаг; по умолчанию `step: 1`.
- Участник может задать собственное `value`: оно побеждает (Member > Entry), а значения остальных участников не сдвигаются, потому что считаются по позиции.
- `start` должен быть `Cp`. Результат проверяется: диапазон Unicode, не суррогат; при попадании на непризначенную кодовую точку (по ICU) загрузчик выдаёт предупреждение.

**2. Шаблонные свойства.** Строковые значения свойств записи (`recipes`, `tags`, строки внутри `Latin("...")` и `Physical("...")` в `binds` и т. п.) могут содержать `{имя}`. Вместо него подставляется одноимённая переменная участника, как уже сделано в `id_template`.

- Переменная это любое поле `Member(...)`, не являющееся известным свойством (`level`, `abbr`, `key`…).
- Ссылки на записи `${id}` остаются отдельным механизмом и шаблонами не затрагиваются. Литеральные фигурные скобки записываются как `{{` и `}}`.
- Неизвестная переменная это ошибка загрузки.
- Если участник сам задал свойство (например, свой `recipes`), оно полностью заменяет шаблон записи.

```ron
Entry(
    id_template: "ipa_n_let_tone_bar_{level}",
    value_sequence: (start: Cp(0x02E5)),
    recipes: ["tn {abbr}"],
    binds: [Bind(mode: Domain("Ipa"), key: Physical("{key}"), modifiers: [LeftAlt])],
    members: [
        Member(level: "extra_high", abbr: "eh", key: "Digit7"),   // 0x02E5, "tn eh", LeftAlt + Digit7
        Member(level: "high",       abbr: "h",  key: "Digit8"),   // 0x02E6, "tn h",  LeftAlt + Digit8
    ],
)
```

## 5. Типы записей (Источники)

### Тип 1: Одиночная базовая запись

Конкретный самостоятельный символ без вариаций и динамической генерации. Содержит фиксированный `id` и явное значение.

```ron
Entry(
    id: "acute",
    value: Cp(0x0301),
    collections: [Diacritic],                   // Использование Enums
    recipes: ["acute"],
    ui: (
        display_groups: [
            (Forge, [Diacritic]),
            (FastKeys, [Diacritic])
        ]
    ),
    binds: [
        Bind(key: Latin("A"),    modifiers: [RightAlt]),
        Bind(key: Cyrillic("Ф"), modifiers: [RightAlt]),
    ],
)
```

Запись, значение которой не является одним символом:

```ron
Entry(
    id: "cyr_upper_yery_acute",
    value: Seq([0x042B, 0x0301]),               // Ы + combining acute; предкомпозита нет
    normalization: Auto,
    collections: [Cyrillic],
)
```

### Тип 2: Вариативная запись (Member-Type с id_template)

Группирует альтернативные версии базового символа. Использует `id_template` для сборки идентификаторов и `variation_of` для привязки к родителю. Каждый `Member` определяет только локальные свойства вариации и может переопределять любые свойства записи.

```ron
Entry(
    id_template: "acute_{variation}",
    hidden: true,
    variation_of: "acute",                      // Связь с базовым родителем
    collections: [Diacritic],
    members: [
        Member(variation: "uncombined", value: Cp(0x00B4)),
        Member(variation: "modifier", value: Cp(0x02CA), recipes: ["acutemod"]),
    ],
)
```

Значение `variation` рекомендуется брать из реестра видов вариаций (`math_bold`, `circled`, `fullwidth` и т. п.), чтобы по ним можно было фильтровать в поиске и GUI.

### Тип 3: Базовая списочная запись (Member-Type без variation_of)

Простое явное перечисление семантически близких независимых символов, которые не являются чьими-то вариациями. От типа 2 отличается только отсутствием `variation_of`.

```ron
Entry(
    id_template: "dia_mark_{accent}",
    members: [
        Member(accent: "acute", value: Cp(0x0301), recipes: ["acute"]),
        Member(accent: "grave", value: Cp(0x0300), recipes: ["grave"]),
    ]
)
```

### Тип 4: Матричная декартова запись (Matrix)

Математическая генерация непрерывных алфавитных или геометрических сеток. Оси координат, шаг смещения (`offset`) и стартовая точка (`start_codepoint`) определяют результат. Оси задаются **упорядоченным** списком, чтобы генерация была детерминированной.

```ron
Entry(
    id_template: "lat_{case}_letter_{letter}",
    matrix: (
        "letter": [
            (id: "a", offset: 0),  (id: "b", offset: 1),  (id: "c", offset: 2),
            /* ... и так далее до z ... */
            (id: "z", offset: 25)
        ],
        "case": [
            (id: "upper", start_codepoint: 0x0041), // 'A'
            (id: "lower", start_codepoint: 0x0061)  // 'a'
        ]
    ),
    calculation_rule: (
        codepoint: "start_codepoint + offset"
    ),
    options: (
        layout_titles: true,
        layout_titles_as_main: false
    )
)
```

Переменные осей в шаблонах: имя самой оси (`{letter}`) даёт `id` выбранного элемента, как в `id_template`; любое поле элемента оси, не являющееся служебным (`id`, `offset`, `start_codepoint`), тоже становится переменной и доступно как `{имя}` в шаблонных свойствах записи, так же как у `Member` (см. «Сокращённая запись списков members»). Это позволяет описывать рецепты и привязки один раз:

```ron
// Набросок, к IPA-файлу пока не применён
Entry(
    id_template: "ipa_n_let_tone_bar_{level}{form}",
    matrix: (
        "level": [
            (id: "extra_high", offset: 0, abbr: "eh", key: "7"),
            (id: "high",       offset: 1, abbr: "h",  key: "8"),
            /* ... */
        ],
        "form": [
            (id: "",                  start_codepoint: 0x02E5, rc: "tn"),
            (id: "_left_stem",        start_codepoint: 0xA712, rc: "tnl"),
            (id: "_dotted",           start_codepoint: 0xA708, rc: "tnd"),
            (id: "_dotted_left_stem", start_codepoint: 0xA70D, rc: "tndl"),
        ]
    ),
    calculation_rule: ( codepoint: "start_codepoint + offset" ),
    recipes: ["{rc} {abbr}"],
    // binds: модификаторы формы (LeftAlt, RightAlt + LeftAlt, CapsLock) переменной ячейки не выразить, см. открытые вопросы
)
```

Известная неудобная деталь: у «простой» формы пустой `id` и суффиксы с `_` внутри id. Если матрица с пустым элементом оси окажется нечитаемой, остаётся вариант из нескольких записей с `value_sequence`.

### Тип 5: Смешанная матричная запись (Fixed / Computed)

Расширение типа 4. Общее `calculation_rule` служит значением по умолчанию для ячеек, а отдельные ячейки переопределяют его готовой точкой (`Fixed`) или вычислением (`Computed`) через алгоритмы Rust.

```ron
Entry(
    id_template: "lat_{case}_letter_some_exotic",
    matrix: (
        "case": [
            Member(id: "c", value: Fixed(Cp(0xA766))),
            Member(id: "s", value: Computed(base: "latin:s_letter_x", mod: "diacritic:acute"))
        ]
    )
)
```

`Fixed` принимает любое `Value` (`Cp`, `Chr`, `Seq`, `RawTxt`). `Computed` возвращает `Precomposed | Sequence`, а не число.

### Тип 6: Ссылочная матрица (Referenced Matrix)

Перекрёстная сборка составных символов по динамическому связыванию (Late Binding). Находит уже инициализированные базовые символы и модификаторы по пространству имён и маске, пробрасывает их переменные, сливает метаданные (рецепты) и вычисляет значение через NFC.

Типичный случай: взять базовый символ, взять всё пространство имён диакритики и автоматически получить записи для всех существующих монолитных акцентированных символов.

```ron
Entry(
    id_template: "lat_{case}_letter_a_with_{accent}",
    referenced_matrix: (
        "base": (
            entry_id_pattern: "latin:{case}_letter_a",
            variables: ["case"]
        ),
        "modifier": (
            entry_id_pattern: "diacritic:{accent}",     // Всё пространство имён diacritic
            variables: ["accent"],
            filter: (collections: [Diacritic], hidden: false)  // Вариации и скрытые записи исключаются
        )
    ),
    merging_rules: (
        recipes: Template(["${base}${modifier}"]),      // Подстановка значений: для a + acute получится "a${diacritic:acute}"
        value: Compose(
            normalization: Nfc,
            on_unresolved: Skip                         // Нет предкомпозита: запись не создаётся
        )
    ),
    options: (
        layout_titles: true
    )
)
```

Правила:

- Сборка идёт по пересечению переменных (join): для каждой пары «база + модификатор» создаётся запись.
- `on_unresolved` определяет поведение, если NFC не даёт одного символа: `Skip` (пропустить запись, значение по умолчанию), `KeepSequence` (сохранить как `Seq`) или `Error`.
- Если база или модификатор не найдены, комбинация пропускается с предупреждением в логе загрузки.
- Зависимости образуют граф: записи разворачиваются в топологическом порядке, циклы обнаруживаются и отклоняются.
- `Template` собирает рецепт из шаблона, где `${base}` и `${modifier}` обозначают найденные записи (по именам осей `referenced_matrix`). Подстановка работает так же, как в обычных рецептах: вместо ссылки встаёт значение записи. Итог соответствует рецепту вида `A${diacritic:acute}`.
- `Append(from: [...])` остаётся вариантом для случаев, когда нужно склеить уже готовые рецепты источников, перебрав все сочетания.

#### Идентификаторы и состав составных записей (предложено)

- **Формат id.** Id составной записи собирается из id базы и локальных id меток через `+`: `latin:upper_letter_a+breve+acute`. Разделитель `+` зарезервирован (раздел 2).
- **Составная запись это полноценная запись.** Запись `latin:upper_letter_a+acute` создаётся при инициализации, как и все остальные, существует сама по себе и имеет собственные свойства (теги, рецепты, привязки), например сгенерированный тег «Заглавная буква латиницы „А“ с акутом». Обращение к ней идёт по её id напрямую, на лету ничего не собирается. Поле `composition: (base: <полный id>, marks: [<полные id>])` нужно лишь затем, чтобы GUI, поиск («все с бреве») и обратный поиск знали состав из данных, а не разбирали строку id.
- **Генерация идёт уровнями.** Юникод раскладывает `Ắ` как `Ă` + acute, поэтому метки добавляются к составным записям предыдущего уровня, а id получается рекурсивно: `{id предыдущего}+{метка}`. Уровень задаётся фильтром по глубине. Одинаковые значения, достижимые разными порядками меток, ловит валидация дубликатов по значению.
- **Что для этого нужно.** В `id_template` должны быть доступны `{base}` и `{modifier}` (локальный id найденной записи), а в фильтре глубина. Примеры типа 6 выше пока написаны в прежней форме и будут приведены к этой после подтверждения.

### Тип 7: Сегментированная запись (Вектор диапазонов / Packed Range)

Группа символов со сквозной логической индексацией (`index`), разорванная Юникодом на физические фрагменты. Описывает карту интерполяции логических индексов на физические стартовые адреса.

```ron
Entry(
    id_template: "archaic_sign_{index}",
    generator: PackedRange(
        total_count: 20, // Логические индексы 0..19
        unicode_spans: [
            (index_start: 0,  index_end: 14, codepoint_start: 0x1BF0), // Кусок 1
            (index_start: 15, index_end: 19, codepoint_start: 0xA800)  // Кусок 2 (прыжок через пропасть)
        ]
    )
)
```

## 6. Переопределения (overrides)

Матрицы описывают регулярные сетки, но Unicode содержит исключения: в Mathematical Alphanumeric Symbols курсивная `h` (U+1D455) зарезервирована, а используется `ℎ` (U+210E). Для таких случаев матрицы получают блок `overrides`, адресующий конкретную ячейку по значениям осей:

```ron
Entry(
    id_template: "math_{style}_letter_{letter}",
    matrix: ( /* ... оси style и letter ... */ ),
    calculation_rule: ( codepoint: "start_codepoint + offset" ),
    overrides: [
        (cell: ("style": "italic", "letter": "h"), value: Cp(0x210E)),
        (cell: ("style": "italic", "letter": "h"), recipes: ["hplanck"]),
    ],
    exclude: [
        ("style": "some_style", "letter": "q"),          // Комбинации, которых не существует
    ],
)
```

- `overrides` меняют любые свойства одной ячейки или набора ячеек (значение, рецепты, привязки).
- `exclude` исключает несуществующие комбинации.
- Приоритет: `overrides` > Member/ячейка > Entry > значения по умолчанию файла.

### Вариации матрицей

Регулярные наборы вариаций (Mathematical Alphanumeric Symbols, fullwidth, circled, parenthesized, tag и др.) описываются одной матрицей: ось букв и ось «форм», где каждая форма задаёт регистр, вид вариации и **стартовую кодовую точку**. Остальное считает `calculation_rule`, а родитель указывается шаблонным `variation_of`. Дыры Unicode закрываются `overrides`. Набор форм у регистров может быть разным (regional indicators и outlined есть только у заглавных), для этого не нужен `exclude`: ненужных форм в списке просто нет.

```ron
Entry(
    id_template: "lat_{case}_letter_{letter}_{variation}",
    variation_of: "latin:{case}_letter_{letter}",
    hidden: true,
    matrix: (
        "letter": [ /* a..z со смещениями 0..25 */ ],
        "form": [
            (id: "math_bold_upper", case: "upper", variation: "math_bold", start_codepoint: 0x1D400),
            (id: "math_bold_lower", case: "lower", variation: "math_bold", start_codepoint: 0x1D41A),
            /* ... */
        ],
    ),
    calculation_rule: ( codepoint: "start_codepoint + offset" ),
    overrides: [
        (cell: ("form": "math_script_upper", "letter": "b"), value: Cp(0x212C)),   // ℬ
    ],
)
```

Нерегулярные наборы (modifier, small_capital, subscript, combining) остаются списками `members` с тем же шаблонным `variation_of`, но через переменную участника: `variation_of: "latin:lower_letter_{letter}"`, `Member(letter: "a", value: Cp(0x1D43))`. Полный пример: `latin_variations.ron`.

Для пользовательских файлов, меняющих записи базового набора, предлагается отдельный режим `patch` (запись с полным id цели и изменяемыми свойствами). Пока не обсуждалось.

## 7. Enums: коллекции, группы отображения, наборы ввода

В данных они записываются идентификаторами, как и раньше:

```ron
collections: [Diacritic],
ui: ( display_groups: [(Forge, [Diacritic]), (FastKeys, [Diacritic])] ),
binds: [Bind(key: Latin("A"), modifiers: [RightAlt]), Bind(key: Hellenic("α"), modifiers: [RightAlt])],   // Значение в скобках это реальный символ набора
```

- **`collections`**: логические коллекции символов.
- **`display_groups`**: пара «вкладка GUI, группа в списке символов». Определяет, где запись отображается в интерфейсе. Вкладка сама знает, какое свойство читать (`recipes`, `binds` и т. д.). Группы модификаторов больше не подставляют: они определяют только место записи в интерфейсе.
- **Наборы ввода** в `key` бинда (`Latin`, `Cyrillic`, `Hellenic`, …): набор определяет, к какой раскладочной семантике относится клавиша.

Расширяемость: ядро знает встроенные значения, а новые коллекции, группы и наборы регистрируются модами на языке Rune без перекомпиляции. Для этого в Rust-представлении каждому enum добавляется открытый вариант вида `Custom("id")`, который заполняется из реестра, пополняемого модами.

## 8. Бинды (привязки клавиш)

Бинд задаёт комбинацию, которая вводит символ записи. Он заменяет `options.fast_key` и `alt_layout_key` старой программы. Бинд одновременно показывается в GUI и регистрируется как реальная комбинация, а группы отображения модификаторов не подставляют.

### Структура

```ron
binds: [
    Bind(key: Latin("A"), modifiers: [RightAlt]),                    // режим Default
    Bind(mode: Domain("Ipa"), key: Physical("Digit7"), modifiers: [LeftAlt], locks: [CapsLock]),
],
```

| Поле         | Значение                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mode`         | [= `Default`] `Default` (всегда активный режим, прежние «Fast Keys») \| `Domain("Имя")` (активируемый режим домена, например `Ipa`, `GermanicRunes`) \| `IME("Имя")` (активируемый режим IME, например `Vietnamese`, `HanyuPinyin`). Имена берутся из реестра, пополняемого модами на Rune |
| `id`           | [нет] Идентификатор бинда. Нужен как адрес для переопределения в отдельных файлах (запись + `id`)                                                                                                                                                                                                                                                                 |
| `target_entry` | Полный id записи. Внутри записи выводится из неё, в отдельных файлах биндов обязателен                                                                                                                                                                                                                                                                                  |
| `key`          | Клавиша (см. ниже). Обязательна во всех режимах, кроме IME                                                                                                                                                                                                                                                                                                                                          |
| `modifiers`    | [= `[]`] Список модификаторов                                                                                                                                                                                                                                                                                                                                                                                            |
| `locks`        | [= `[]`] Список включённых состояний                                                                                                                                                                                                                                                                                                                                                                               |
| `input`        | [предложено] Только для IME: последовательность элементов вместо одной клавиши                                                                                                                                                                                                                                                                                                |

Допустима и сгруппированная запись `Mode(Default, [Bind(...), ...])`, как в отдельных файлах биндов; в записи символа короче плоская.

### Клавиша (`key`)

- Варианты: `Latin("A")`, `Cyrillic("Ф")`, `Hellenic("α")`, `Physical("KeyA")`, `Custom("set", "key")`. Все принимают строку, поэтому работают шаблоны и реестр модов.
- **Именованные наборы** (`Latin`, `Cyrillic`, …) обозначают символ клавиши без Shift в активной раскладке. Набор может покрывать несколько раскладок (например, Dvorak входит в `Latin`); перечень задаётся отдельно. Буквы записываются в верхнем регистре, а регистр результата определяют Shift и `locks`.
- **`Physical`** обращается не к раскладке, а к положению клавиши на физической клавиатуре. Имена предложено брать по W3C `KeyboardEvent.code` (`KeyA`, `Digit7`, `BracketLeft`, `Space`, `F1`). Клавиши без печатного символа задаются только так.
- Одна клавиша записывается одним способом (`Latin("[")`, а не `Latin("LeftBracket")`), иначе потребуется отдельная проверка на дубликаты.

### Модификаторы и locks

- `modifiers`: `Alt`, `LeftAlt`, `RightAlt`, `Control`, `LeftControl`, `RightControl`, `Shift`, `LeftShift`, `RightShift`, `Super`, `LeftSuper`, `RightSuper`. Сокращения AutoHotkey (`!`, `^`, `+`, `<`, `>`) не используются. Предложено: имя без стороны (`Shift`) означает любую сторону, в том числе обе.
- `locks`: `CapsLock`, `NumLock`, `ScrollLock`. Это состояние, а не удерживаемая клавиша; в старой программе CapsLock обозначался `c*`.

### Правила совпадения (Shift и CapsLock)

Для одной клавиши возможны до восьми комбинаций:

|                           | без Shift          | `LeftShift`              | `RightShift`              | `LeftShift` + `RightShift`         |
| ------------------------- | --------------------- | -------------------------- | --------------------------- | -------------------------------------- |
| CapsLock выключен | `Bind()`            | `modifiers: [LeftShift]` | `modifiers: [RightShift]` | `modifiers: [LeftShift, RightShift]` |
| CapsLock включён   | `locks: [CapsLock]` | то же с `locks`     | то же с `locks`      | то же с `locks`                 |

Вместо трёх правых столбцов можно задать один бинд на `Shift`.

- Явный бинд с Shift (`Shift`, `LeftShift`, `RightShift`) приоритетнее любого запасного поведения.
- Если явного бинда на Shift нет, нажатие Shift вводит то же, что и при включённом CapsLock: срабатывает бинд с `locks: [CapsLock]` и теми же остальными модификаторами.
- Отсутствие `CapsLock` в `locks` означает, что CapsLock выключен (предложено; следует из перечня комбинаций, нужно подтвердить).
- Более конкретный бинд (с указанием стороны) приоритетнее общего `Shift` (предложено).

### Режимы

- **Default** всегда активен (прежние «Fast Keys»).
- **Domain** и **IME** активируются отдельно. Для Domain бинд тоже одна клавиша с модификаторами: она прямо вводит символ.
- **IME** работает по другой механике: поток поступающих символов даёт другой символ. Логика ветвится по `mode`. Предложено задавать вход последовательностью элементов, где элемент это клавиша или ссылка на символ: `input: [Latin("a"), Latin("w"), Latin("s")]` и `input: [Sym("latin:lower_letter_a+breve"), Latin("s")]` дают один и тот же `ắ` независимо от того, пришёл `ă` по клавишам `a`, `w` или по `RightAlt + A`. Концепция IME не доработана, возможен полный переход на символьное определение.

## 9. Пайплайн загрузки

1. **Declaration.** RON-файлы десериализуются в декларации (то, что написано в файле).
2. **Развёртывание.** Генераторы (`Members`, `Matrix`, `ReferencedMatrix`, `PackedRange`) разворачиваются в плоские записи. Типы 6 обрабатываются после остальных, по графу зависимостей. На этом же шаге вычисляются `value_sequence` и шаблонные свойства (`{имя}`); подстановка ссылок `${id}` в рецептах выполняется после них, когда все записи уже существуют.
3. **Symbol.** Получается плоская разрешённая запись со значением (`Value`), рецептами, привязками и свойствами. Нормализация применяется на этом этапе. Записи хранятся как пары «полный id → Symbol»: id и пространство имён в самой записи не дублируются.
4. **Валидация.** Проверяются дубликаты id, дубликаты значений у разных id, непризначенные code points, корректность графем, неразрешённые ссылки и циклы.
5. **Индексы.** Хранилище записей само является индексом по полному id (хэш-таблица, доступ без обхода записей). Дополнительно строятся индексы по значению (в нормализованной форме), по токенам поиска и по рецептам.

Разрешённый результат можно кэшировать в бинарном виде с привязкой к версии файлов и версии таблиц Unicode.

## 11. Открытые вопросы

1. **Уровень рецептов.** Предполагается, что рецепт сопоставляется с *текстом*, получаемым после системной раскладки, а привязки (`binds`) работают на уровне клавиш. Это нужно подтвердить.
2. **Режимы обработки рецептов** (регистр, порядок, особые режимы для Vietnamese/Pinyin) пока не описаны; их придётся добавлять отдельным полем рядом со строкой рецепта.
3. **Режим `patch`** для изменения базовых записей пользовательскими файлами и модами.
4. **Матрица вместо нескольких записей** для четырёх форм тональных линий IPA (набросок в разделе про тип 4): подтвердить, стоит ли переходить на неё, учитывая пустой `id` у простой формы.
5. **Общие оси.** Ось `letter` (a–z со смещениями) повторяется в `latin_cocept` и в матрице вариаций. Возможно, оси стоит выносить в именованные наборы и подключать по имени.
6. **Нужны ли `schema_version` и `requires`** в метаданных файла, или достаточно версии всего пакета данных.
7. **Бинды: состояние CapsLock.** Что вводит Shift при включённом CapsLock, если явного бинда нет (поведение ОС с инверсией или бинд с `CapsLock`). Как трактуются `NumLock` и `ScrollLock`, если их нет в `locks`.
8. **Бинды: подстановка модификаторов.** Переменная участника подставляется только в строки, а `modifiers` это enum. Нужна строковая форма модификаторов или другой способ, чтобы выразить четыре формы тональных линий одной матрицей.
9. **Бинды: IME.** Формат `input` и ссылки на символы (`Sym`), символьное или клавишное определение, ветвление по `mode`.
10. **Бинды: хранение и взаимодействие с ОС.** Индекс биндов, отдельные файлы и переопределение по `id` (отдельная тема), а также конфликт AltGr на Windows (приходит как `LeftControl + RightAlt`).
